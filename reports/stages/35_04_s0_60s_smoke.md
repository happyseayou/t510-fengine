## 1. 本步目标

检查，实测 10 ms 全频段累加的 CPU、NIC、ring、队列和磁盘行为。本步不评价 ADC 噪声
“通过/失败”。

- `clock_reference=onboard_tcxo`，外部 10 MHz/PPS 断开；
- 8 路独立 50 Ω、DAC 物理断开、空调与环境状态；
- 采集机可用空间、文件系统、receiver commit 和 writer 配置。

## 3. 证据要求

- NIC/kernel/ring/worker/application drop 与 16 flow 连续性前后快照；
- CPU、队列 high-water、落盘速率、fsync/chunk 延迟和可用空间变化；

### 5.4 对“必须整板断电”的审计修正

用户当前无法断电，并把“不掉电热更新”列为正式目标。进一步审计后，前一版把物理 power
cycle 写成“唯一恢复入口”证据不足，应撤回：第三次失败只证明 Linux warm reboot 不会复位
RFDC 模拟/时钟域，也证明**当前 CONFIGURE 路径**会稳定复现故障；它不能证明板卡必须掉电。

AMD PG269 把 RFDC 上电状态 `6-10`定义为 Clock Configuration：状态机先检测转换器输入是否有
good clock，再检查 tile PLL 并向数字部分释放时钟。AMD 驱动的`XRFdc_Reset`会把 tile 从
state 0完整跑到state 15，`XRFdc_WaitForRestartClr`超时时打印当时的current state。因此本次
state 6的直接含义是RFDC IPSM没有越过时钟配置段，不是驱动宣告“只能断电恢复”。官方依据：

- [PG269 Power-on Sequence Steps](https://docs.amd.com/r/en-US/pg269-rf-data-converter/Power-on-Sequence-Steps)；
- [PG269 Restart Tile](https://docs.amd.com/r/en-US/pg269-rf-data-converter/Restart-Tile)；
- [AMD RFDC driver `xrfdc.c`](https://github.com/Xilinx/embeddedsw/blob/master/XilinxProcessorIPLib/drivers/rfdc/src/xrfdc.c)。

本仓库调用链存在一个与现场高度吻合的时钟破坏窗口：

1. `FEngineController.prepare()`默认`fresh_download=True`且
   `force_clock_reconfigure=True`；
2. overlay下载完成后，`apply_sysref_locked_observation_config()`即使发现当前已经是目标
   `onboard_tcxo` profile，也会调用完整`configure_clock()`；
3. 完整profile写入会先把LMK RESET拉高50 ms、再拉低50 ms，然后重写整个寄存器表；
4. 它随后调用八个tile的`XRFdc_Reset`，本次DAC0就在此处停于state 6。

v42 ADC-only现场旧状态与v34 Stage 35需要的时钟实际上相同：都是
`160m_10m_request_manual_clkin0`、RFDC 3.84 GS/s和PL 160 MHz；160/320 MS/s只是PL science
模式选择，不要求改LMK。当前`/run/t510-clock-active-profile.json`也记录了该目标profile和
register SHA，但watchdog因PYNQ active-bit状态不可用而处于`WAITING_FOR_PL`，所以此文件只作
失败现场证据，不能替代下一次执行前的实时双PLL与寄存器签名门禁。

仓库既有[Stage 34c-2](34c-2_clock_sysref_causality.md)实机记录也已经证明：overlay运行后再完整
重写LMK会导致同类state-6故障；真正需要换时钟profile时，可以在旧时钟仍存在时先shutdown
旧tile，再写LMK、等待双锁、按需请求SYSREF，然后重载overlay并完成RFDC/MTS。这构成“不掉电
恢复”已有的工程先例。

### 5.5 不掉电热恢复设计（随后已实现）

第一选择是新增显式的`clock-preserving hot update`事务，不修改当前板端硬件状态后直接重试
旧CONFIGURE：

1. 保持STOP、DAC数字mask为0、receiver未arm；停止所有非正式Agent/watchdog，取得CONFIGURE
   独占锁；
2. 实时读取LMK关键寄存器、selector GPIO、PLL1/PLL2；只有profile ID和register SHA精确等于
   `160m_10m_request_manual_clkin0`且双锁时才允许`clock_action=preserve`，否则fail-closed；
3. 在**不触碰LMK RESET、不重写LMK表**的前提下重新下载相同SHA的v34 bitstream；
4. 重新attach新overlay，调用`prepare(fresh_download=False,
   force_clock_reconfigure=False)`，配置mixer/NCO并执行request-SYSREF MTS；该分支不得调用
   `XRFdc_Reset`；
5. 逐项验证八个tile state 15、tile PLL、16/16 valid、MTS `416/112`、bit/core/profile身份和
   DAC mask 0，全部通过才签发一次性START事务；任何失败保持STOP，不自动回落到完整LMK重写。

审计时的`force_clock_reconfigure=False`分支只检查`configured`和`selected_ref`，尚未严格核对
`clock_profile`/SHA；因此当时没有仅通过改变HTTP参数直接上板，而是先补齐事务、门禁、失败
日志和测试。实现及实机结果见5.7节。

若未来确实要切换LMK profile，则使用Stage 34c-2已经定义的原子handoff：STOP → 在旧时钟下
shutdown tile → 写新LMK并确认双锁 → SYSREF request → overlay reload → RFDC reset/MTS →
SYSREF off。不得先下载overlay再改LMK。

`XRFdc_StartUp`、Master Reset和`XRFdc_CustomStartUp`不作为当前首选恢复方式：历史现场已有简单
Shutdown/StartUp卡state 6的负证据；Master Reset同样从state 0启动并依赖good clock；PG269虽
定义CustomStartUp，但板上PYNQ 3.0.1的Python wrapper及`libxrfdc.so`均未导出该符号，需要另行
升级/绑定和资格测试。

### 5.6 热更新支持边界与资格矩阵

这里的“热更新”定义为**整板不断电、允许受控STOP和短时数据中断**。单板完整PL bitstream
重载会中断数据面，不能承诺hitless；零丢包业务切换需要双板冗余，或者今后把可更新逻辑隔离
成partial-reconfiguration区域。

在把该能力标为SUPPORTED前，至少完成：

1. v34 → 同SHA v34保持时钟热重载20/20；
2. v42 ADC-only → v34、相同时钟profile热更新20/20（本次真实迁移路径）；
3. 仅Agent升级、不重载bitstream的独立路径；
4. 相同profile preserve与真实profile transition分别测试，禁止隐式互相回落；
5. 每个事务checkpoint故障注入，确认始终STOP、DAC全零、无UDP和可追溯handoff journal；
6. 每轮核对bit/core/profile、tile state/PLL、16/16 valid、MTS target以及20或60 s无drop/gap
   门禁。

本轮最终完成了一次同SHA v34保持时钟的受控实机恢复；这证明路径可行，但尚未完成上述20/20
资格矩阵，因此能力分类为`EXPERIMENTAL / NON_HITLESS`，不能写成全面`SUPPORTED`。

### 5.7 clock-preserving实现与实机恢复

控制面新增显式`update_mode=clock_preserving`，并要求请求同时声明
`receiver_stream_accepting=false`。该模式不会隐式回退到完整时钟配置：

- CONFIGURE前直接读取LMK关键寄存器、profile SHA、selector GPIO、RESET、SYSREF request和
  PLL1/PLL2；任一身份或锁定不符即`HOT_UPDATE_CLOCK_PREFLIGHT_FAILED`；
- `prepare_clock_preserving_hot_update()`只重载目标bitstream，随后以
  `fresh_download=false, force_clock_reconfigure=false, require_clock_preserved=true`attach和

- `/var/lib/t510/hot-update-state.json`按

### 5.12 丢失根因与10 ms热路径优化

采集机不是同构20核：CPU 0–4、10–14容量约718–731、最高2.808 GHz，CPU 5–9、15–19容量
约997–1024、最高3.9 GHz。ConnectX提供20个combined RX queue，每个queue的IRQ固定在同号
CPU；服务则启动24个fanout worker并使用`--pin-workers off`。此外，fanout socket由24个并发
线程注册，kernel fanout成员次序不保证等于程序worker id，因此不能未经修复便把旧`auto`
绑核当成可靠的queue/worker一一对应关系。

这解释了“以前全速接收正常”与本次现象并不矛盾。Stage 33的全速门禁主要执行包解析、连续性
统计和稀疏Web preview；Stage 35首次对每个SPEC包的2048个复数cell全部执行均值与二阶矩。
320 MS/s下16个block合计约1.25 Mpacket/s，即约25.6亿cell/s。优化前15 s诊断扫描
`stage35-opt-baseline-20260830-232000`的`pidstat`平均CPU为`1025.62%`，多个worker瞬时达到
`99–101%`；`perf`用户态采样的主热点正是每cell在线Welford的`mean_P/M2_P`依赖链。物理NIC
仍为0 drop，但账本缺32,308/18,750,000帧。

receiver二进制随后作两项不改变10 ms科学产品的修正：

1. 桶内热路径用整数精确矩保存`sum(I)`、`sum(Q)`、`sum(P)`和`sum(P²)`；桶结束时以
   `M2 = (n*sum(P²)-sum(P)²)/n`一次性生成二阶矩。分子在`u128`中先精确相减，再转为
   `f64`，因此大直流、小方差情形不发生普通两遍浮点公式的灾难性抵消。100 ms最大原生桶
   明确限制为7,813帧，所有整数和分子均有界；白/粉/漂移/脉冲/正弦、极值和大直流小方差
   oracle全部继续通过。
2. arm到首个正式桶的worker预热提前量由2个桶增为10个桶。10 ms模式只把正式曝光起点延后
   到arm后100 ms，原生积分宽度仍严格为10 ms。优化后但尚未增加提前量的15 s诊断已经做到
   receiver kernel/ring drop增量0、无稳态gap；仅3个block从同一正式起点分别缺444/1,311/
   1,933帧，证明残余是worker观察新generation的起始偏斜，而非10 ms持续处理能力不足。
